🌟 myPlan
==============

**목적 기반 자동 루트 추천 서비스**

현재 위치를 기준으로 **병원 / 공중화장실 / 약국 / 편의점**  등 목적을 선택하면  
근처의 목적지를 **안내**해주는 가벼운 라이트 서비스입니다.

* * *

🎯 기획 이유
--------

일상 속에서 자주 겪는 고민들:

*   “지금 갈 수 있는 공중화장실이 어디있지?”
*   “가까운 약국이나 편의점은 어디있지?”

기존 지도 앱들은 장소 정보 제공 위주이기 때문에  
**상황 기반 루트 추천**이 부족하다는 문제가 있습니다.

그래서 **myPlan**는 사용자가 목적만 선택하면  
생각할 필요 없이 **바로 이동할 수 있는 단 추천 루트**를 제공합니다.

> 많은 옵션보다, 지금 당장 움직일 수 있는 단 하나의 루트가 더 중요하다.

* * *

🛠 프로젝트 목표
----------

*   사용자의 현재 위치 기반으로 목적에 맞는 **최적 루트 1개 생성**
*   복잡한 검색이나 필터링 없이 **초간단 UX 제공**
*   지도 기반으로 경로와 장소를 직관적으로 시각화
*   모바일에서도 사용하기 좋은 반응형 UI 구성
*   짧은 시간에 **빠르고 명확한 경험** 제공

🔧 기술적 개선
--------

### ✔ T Map API 경로 요청 캐싱 개선

Lighthouse 성능 측정 과정에서 한 번의 검사마다  
T Map API 경로 요청이 반복적으로 발생하는 문제를 발견

실제 보행 경로 데이터를 가져오는 T Map API 요청에는 캐싱이 적용되어 있지 않아  
동일한 경로 조건에서도 불필요한 API 호출이 반복되고 있었다

이 문제는 단순한 성능 저하뿐 아니라  
외부 API 사용량 증가와 과금 리스크로 이어질 수 있었기 때문에,  
경로 요청 흐름을 캐싱 중심으로 재정리 하였다.

개선 과정에서는 컴포넌트 내부의 API 호출 구조를 정리하고,  
요청 조건을 기준으로 이미 조회한 경로 데이터는 재사용되도록 변경했다.

그 결과, 기존에는 장소를 변경할 때마다 API 응답을 기다리는 동안  
Loading 컴포넌트가 노출되었지만,  
캐싱 처리 후에는 이미 조회한 경로 데이터가 즉시 반영되어  
더 빠르게 느껴지는 사용자 경험을 제공할 수 있었습니다.

#### 개선 결과

*   동일 경로 조건에서 반복 발생하던 T Map API 호출 감소
*   장소 변경 시 불필요한 Loading 상태 노출 감소
*   외부 API 사용량 증가에 따른 과금 리스크 완화
*   캐시된 경로 데이터를 활용한 빠른 경로 전환 경험 제공


### ✔ 지도 렌더링 책임 분리 및 지도 객체 재생성 최소화

기존에는 `RoutePlace` 컴포넌트가 장소 조회, 지도 생성,  
현재 위치 마커 생성, 경로 렌더링까지 모두 담당했다.

이 구조에서는 장소 목록 UI와 지도 렌더링 로직이 하나의 컴포넌트에 섞여 있어  
컴포넌트의 책임이 커지고, 경로 변경이나 장소 변경 시  
지도 객체가 불필요하게 다시 생성되거나 중복 렌더링될 가능성이 있었다.

이를 개선하기 위해 장소 목록과 사용자 인터랙션은 `RoutePlace`가 담당하고,  
지도 생성과 마커, Polyline 렌더링은 `RouteMap`이 담당하도록 역할을 분리했다.

또한 경로를 그릴 때 생성되는 Polyline과 Marker 객체의 참조를 관리할 수 있는 구조를 마련해,  
경로가 변경될 때 기존 지도 객체를 정리하고 새로운 경로를 그릴 수 있도록 개선했다.

#### 개선 결과

- 장소 목록 UI와 지도 렌더링 로직의 책임 분리
- 지도 객체의 불필요한 재생성 가능성 감소


### ✔ Lighthouse 기반 성능 분석 및 경로 API 호출 구조 개선


기존에는 `A → B`, `B → C`처럼 장소 간 경로가 필요할 때마다  
클라이언트에서 T Map API 요청을 각각 발생시키는 구조였다.  
선택된 장소가 많아질수록 최대 5번의 경로 API 호출이 발생할 수 있었고,  
이는 브라우저 부담과 네트워크 요청 증가로 이어질 수 있다고 판단했다.

이를 개선하기 위해 경로 호출 로직을 서버 API 단으로 이동했다.  
클라이언트는 현재 위치와 장소 좌표만 서버로 전달하고,  
서버에서 경로 요청 데이터를 구성한 뒤 T Map API를 호출하도록 변경했다.

그 결과 클라이언트는 여러 번의 경로 요청을 직접 처리하지 않고,  
한 번의 서버 요청만으로 필요한 경로 데이터를 받을 수 있게 되었다.  
이를 통해 클라이언트의 API 호출 부담을 줄이고,  
경로 데이터 요청 흐름을 더 단순하게 만들었다.

또한 UI를 스크롤 방식의 전체 장소 리스트로 변경하는 과정에서  
기존에 사용하던 `totalDistance` 값을 그대로 사용할 수 없는 문제를 발견했다.  
기존 값은 하나의 추천 경로 기준으로 계산된 거리였기 때문에,  
여러 장소를 리스트 형태로 보여주는 UI에서는 각 장소의 개별 거리 정보로 사용하기 어려웠다.

이를 해결하기 위해 T Map 장소 리스트 API의 `radius` 값을 활용해  
각 장소의 거리 정보를 표시하도록 개선했다.

#### 개선 결과

Lighthouse로 개선 전후를 각각 3회씩 측정한 결과,  
아래와 같은 성능 개선을 확인했다.

| 지표             | 개선 전 |      개선 후 |
| ---------------- | ------: | -----------: |
| CLS              |   0.095 |        0.000 |
| Speed Index      |       - | 약 8.3% 개선 |
| 네트워크 요청 수 |       - | 약 6.5% 감소 |

이번 작업을 통해 성능 측정 도구로 실제 병목 지점을 확인하고,  
AI를 활용해 놓칠 수 있는 문제를 함께 점검하며 개선 우선순위를 정리했다.  
단순히 화면을 구현하는 데서 끝나지 않고,  
API 호출 구조와 사용자 경험에 영향을 주는 지점을 함께 개선했다.

### ✔ GPS 기반 현재 위치 마커 이동 기능 구현

지도 위에 표시되는 현재 위치 마커가 사용자의 실제 위치 변화에 따라  
이동하도록 개선했다.

기존에도 현재 위치를 지도에 표시하는 기능은 있었지만,  
사용자가 이동할 때마다 의도하지 않은 문제가 발생할 수 있는 구조였다.  
현재 위치가 바뀔 때마다 T Map API에 새로운 좌표로 경로 요청을 보내고,  
변경된 위치에서 목적지까지의 경로 Polyline을 다시 그리는 흐름이 섞여 있었다.

내가 의도한 동작은 경로를 다시 계산하는 것이 아니라,  
이미 그려진 지도 위에서 현재 위치 마커만 이동시키는 것이었다.  
하지만 기존 구조에서는 현재 위치 변경과 경로 재요청 로직이 분리되어 있지 않아  
지도 전체가 다시 그려지거나 깜빡이는 현상이 발생할 수 있었다.

이를 개선하기 위해 먼저 지도 관련 함수의 역할을 분리했다.  
Marker를 생성하는 함수는 Marker 생성만 담당하고,  
Polyline을 그리는 함수는 경로 렌더링만 담당하도록 리팩토링했다.  
하나의 함수가 여러 역할을 처리하던 구조를 나누면서  
각 로직의 책임을 명확하게 만들었다.

현재 위치 변화 감지는 브라우저의 `watchPosition`을 사용했다.  
`watchPosition`으로 사용자의 위치 변화를 감지하고,  
새로운 좌표가 들어오면 기존 현재 위치 Marker의 좌표만 갱신하도록 구성했다.

또한 Naver Maps 객체는 여러 지도 기능에서 함께 사용되기 때문에  
전역 상태로 관리하도록 분리했다.  
이를 통해 지도 객체를 반복 생성하지 않고,  
이미 생성된 지도 인스턴스를 기준으로 Marker와 Polyline을 제어할 수 있게 했다.

#### 개선 결과

- 사용자의 위치 변화에 따라 현재 위치 Marker가 이동하도록 구현했다.
- 현재 위치 변경 시 불필요한 T Map API 경로 재요청을 방지했다.
- Marker 이동과 Polyline 렌더링의 책임을 분리했다.
- 지도 전체가 다시 그려지며 깜빡이는 현상을 줄일 수 있는 구조로 개선했다.
